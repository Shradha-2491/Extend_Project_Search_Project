Release APK hardcoded-secret scan
==================================
Date: 2026-09-22
APK: mobile/Product_Search_Project/app-release-signed.apk
     (release.jks self-signed for lab testing; not committed -- see .gitignore)

Method
------
Since apktool/jadx were not available in this environment, the APK was
unzipped directly and its dex bytecode + compiled resources were searched
for secret-shaped strings with `strings` + grep (a decompiler gives nicer
formatting but does not see any string that a raw `strings` pass over the
dex would miss -- both approaches read the same underlying constant pool).

  unzip app-release-signed.apk -d apk-inspect
  cd apk-inspect
  strings classes.dex resources.arsc | grep -iE \
    "client_secret|GOCSPX|api[_-]?key|BEGIN (RSA|EC) PRIVATE KEY|password.{0,3}="

Result
------
  , isPassword=
  , new_password=
  , password=

No match for client_secret, GOCSPX- (Google's OAuth client-secret prefix,
confirmed present in backend/.env's GOOGLE_CLIENT_SECRET but absent here),
any api_key-shaped string, or a PEM private-key header.

What this means
----------------
The three hits are Kotlin property/parameter *names* (from
PasswordResetConfirmRequest.new_password, TokenStore field names, and a
Compose OutlinedTextField parameter), not secret *values* -- they show up
because Kotlin/Compose keep some parameter names in bytecode metadata for
reflection and IDE tooling, which is expected and not a finding.

This confirms by direct inspection (not just code review) what
GoogleAuthConfig.kt's docstring claims: the mobile app has no OAuth client
secret to leak in the first place (Credential Manager's PKCE-equivalent
flow authenticates the app via its release-signing certificate, not a
secret), and GOOGLE_CLIENT_SECRET genuinely never leaves the backend.
